# BPS 附件准备与并发配置

适用分支：sever。实现日期：2026-09-28。

同一个请求内重复的图片/文件引用先合并处理，再按原位置重写出站 JSON。普通文件与图片都使用有界并发；文件名、媒体类型和内容共同决定文件上传语义，工具结果保留 call_id。图片与文件统一受账号的“BPS 历史附件精简”开关控制，上传前按其保留规则省略旧内容，详见 codex-bps-mode.md；关闭时不做历史精简。用量计费路径不变。仅有旧账号 file_id 而没有原始内容时，不会伪造可用于新账号的引用，仍受现有切号上下文检查约束。

请求内准备缓存复用解码、MIME 和摘要结果，按完整原始内容与文件名精确匹配，不能只按会话 ID 命中旧正文。缓存不含账号句柄；切号时另行构造目标账号键。最多保留每请求 128 项、8 MiB，进程累计 64 MiB，计入原始输入键及解码数据。请求结束/取消释放。超过保留预算的附件仍受支持，但后续重试可能再次解码；不承诺任意大小附件永不重复解码。

成功句柄缓存与上传中任务分开。后者最多 4,096 个不同键，满时等待并支持取消；不绕过限制直接上传。成功缓存使用 LRU 与惰性过期检查，不随容量扩大而在每次命中时全表扫描。已有共享缓存、分布式租约及失效重传机制继续工作，缓存键格式保持兼容。账号记录不同即分别缓存，即便共享同一工作区。

## 部署参数

系统设置 → Codex → BPS 附件上传与连接并发提供以下参数，存入数据库（支持 PostgreSQL/SQLite），参与配置导入导出，重启保留。保存成功后才更新运行态；保存失败返回错误且继续使用旧值。

| 系统设置 | 默认 | 有效范围 | 作用范围 |
|---|---:|---:|---|
| 单请求附件并发 `bps_attachment_request_concurrency` | 15 | 1–64 | 每请求的图片/文件准备与上传 worker 数；新一批附件处理生效 |
| 每账号同时上传附件数 `bps_attachment_account_concurrency` | 15 | 1–1024 | 同一进程、同一账号记录下所有请求的图片和文件共用额度，超额排队，不占实例上传槽 |
| 实例同时上传附件数 `bps_attachment_instance_concurrency` | 64 | 1–1024 | 每个进程所有账号合计正在上传的附件个数；多个实例分别计数 |
| Resin 每账号连接上限 `resin_account_max_conns` | 15 | 1–1024 | 仅 Resin 反代，按账号隔离、按目标主机限制；替代原固定 10 条连接 |

64 指附件个数，不是 64 个对话任务或 RPM。缓存命中不占上传槽，排队期间不占实际上传槽。实例上限调高会唤醒等待项；调低不会中断在途上传，等待已占用名额自然释放。普通直连和 Resin 均受独立的账号级附件限制。同一账号有多个请求时合计限 15，不是每个请求各有 15；其他账号不会被已满额账号堵住。缓存命中不占账号或实例上传槽。账号级计数按本实例的账号记录 ID 隔离，不是跨实例分布式限流，也不是按工作区合并。Resin 的额度由附件上传和推理等 HTTP 请求共用；保存后后续请求使用新连接池，旧请求继续结束，切换期间两代连接池可能暂时并存。

并发以系统设置为准，不使用同名的并发环境变量覆盖页面。以下缓存和缓冲预算仍通过环境变量配置；未配置或越界时使用默认值。

| 环境变量 | 默认 | 有效范围 | 用途 |
|---|---:|---:|---|
| `CODEX_BPS_ATTACHMENT_CACHE_ENTRIES` | 4096 | 1–65536 | 每实例成功句柄条数上限 |
| `CODEX_BPS_ATTACHMENT_CACHE_MIB` | 64 | 1–1024 | 成功句柄及元数据的估算字节预算 |
| `CODEX_BPS_ATTACHMENT_BUFFER_MIB` | 512 | 64–16384 | 解码准备与活跃上传分别使用的缓冲准入预算 |
| `CODEX_BPS_ATTACHMENT_CACHE_TTL_MINUTES` | 30 | 1–1440 | 既有共享及本地句柄 TTL，默认不变 |

multipart 上传直接组合头部、原始附件字节与结尾，不额外复制整份附件，并保留准确的 Content-Length 和可重放请求体。缓冲准入在完整解码之前执行，保守预留二进制及处理空间；上传还有独立的活跃字节控制。两个阶段的预算不是进程 RSS 的硬上限，原始请求体、解析结果、请求内准备缓存及运行时开销另计。单个满足现有请求大小限制但超过缓冲预算的附件可以独占运行，避免永久等不到准入；不突破既有请求大小限制。

实际上传按等待中的业务请求轮转，避免一个大请求长期独占队列；缓冲准入使用 FIFO。缓存命中、请求内重复引用不占实际 HTTP 上传槽。排队计时不消耗原有单次上传的 60 秒 HTTP 超时；请求取消仍中止等待，共享上传另有 3 分钟总保护时限。并发配置本身不修改错误重试预算。新增的账号级上传限流回退见 [两小时附件回退](bps-attachment-429-fallback.md)，只处理明确匹配的附件上传 429，不处理推理限流或未知 429。

默认值是保守起点，并非 196 GB 服务器实测最优值。可在固定流量下对比单请求 8/15、实例 32/64/128、缓存 4096/8192/16384；一次只改一类参数。缓存容量与 Responses 上下文重建的“本地总预算/L1 单条准入/单次重建上限”无关。

## 诊断与验证

原有请求诊断增加 `attachment_decodes`、`attachment_hashes`、`attachment_deduplicated`、`preparation_reuses`、`buffer_wait_ms`、`upload_queue_ms`、`instance_upload_limit`、`account_upload_limit`。重复引用计入去重数，不伪装成额外的缓存查询；`images/files.upload_reused` 仍统计最终引用复用数。既有缓存命中、真实上传次数、上传耗时和准备壁钟耗时继续保留。所有字段不包含原始附件、文件名、摘要或句柄。

正确性检查包含：旧 UUID 窗口切号、严格/冲突拒绝、归属恢复、同请求 A→B→A 的账号隔离与准备复用、重复引用位置保留、工具与文件载体、失效句柄精确清理、共享上传取消、成功缓存不被失败上传淘汰、队列公平性及内存准入释放。缓存命中基准覆盖 256/4096/16384 条。

不据此承诺整机 RPM 提升倍数。生产收益需观察成功请求吞吐、附件准备 P95/P99、实际上传次数、CPU/RSS、GC 和队列时间；计费与 Token 仍采用原有路径。
