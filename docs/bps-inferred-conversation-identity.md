# BPS conversation hints without client session IDs

The account's `codex_fingerprint_mode=session` (Device + session) now opts ordinary BPS requests into a stable outbound session hint when the client has no explicit session identity. Native Codex, relay accounts, and the off/device modes retain their existing behavior. The full mode keeps the separate account-wide outbound BPS task policy documented in `codex-bps-mode.md`; its account selection can use the same caller-scoped task hint described below. No default setting changes.

A valid inbound `metadata.task_id` is used first, scoped to the authenticated caller. Without it, the hint is scoped to the authenticated caller, optional installation/device ID, inbound UA, leading instructions/system messages and first user message. Verified NewAPI user identity is included; direct callers are separated by their Codex2API key. A signed installation ID takes precedence over client hints. A generic relay UA does not count as a device ID. Device IDs may be absent: in that case the caller and opening still partition the hint, with the weaker source recorded in diagnostics.

BPS then applies its existing account/profile cache partitioning. Within that partition, appending turns keeps task_id stable. Word now sends durable UUIDv7 task/turn metadata without Session-Id or prompt_cache_key; missing turn IDs are inferred from the latest user boundary so tool continuations retain their turn. Other profiles retain their existing Session-Id, prompt_cache_key and generated-turn behavior. Changes to models or tool declarations alone do not change the opening hint. The existing account-identity epoch mapping still applies.

Explicit session/cache IDs and resolved roots take precedence. Conflicting identity, local-only affinity overrides, related/internal requests, compaction and previous_response_id continuations are not inferred. This hint is never inserted into inbound metadata, NewAPI signatures, root ownership, session-window accounting, or authorization. It does not change retry or policy-refusal handling.

Diagnostics appear under `upstream.bps_compat.inferred_session`: result, skip reason, source, device_source, ua_included and heuristic. They contain no raw prompt, device ID, UA, or user identity. The actual outbound identifiers remain in the existing outbound identity diagnostic.

This is a heuristic, not a recovered conversation ID. Two independent chats with the same user/device/UA and identical opening share a hint. Changing the UA or opening instructions, or omitting/truncating the opening history, can change or disable the hint. For guaranteed separation and continuity, callers must send their own stable session ID. Shared direct API keys cannot distinguish end users who provide identical hints.

Validation uses local mock transports only: cross-turn reuse, caller/device/opening/account/profile separation, explicit-ID precedence, exclusions, logging and unchanged disabled modes. It does not establish upstream cache hits or explain upstream 403 policy errors.

## Soft account preference

For BPS accounts in `session`, `full` or `round` mode, the pre-dispatch task hint now participates in account selection while global session affinity is enabled. The gateway first tries the account previously associated with that hint, then uses normal scheduling when it is unavailable, excluded, at capacity, outside the authorized group or unable to serve the model. The initial selection still follows the normal balancing policy. The request and response bytes are not changed by the preference. Rotating a `round` task batch does not rotate this caller-scoped routing hint or force an account switch.

The preference is stored separately in `bps_task_affinities` (task key, account ID, revision), shared by instances using the same database and retained across restarts. Compare-and-update prevents a late request from overwriting a newer switch. Concurrent first requests can make different choices before the first preference is saved; subsequent requests reuse the saved winner. Storage failure falls back to ordinary scheduling and is visible in diagnostics.

This is not the account-wide outbound `task_id`: that value requires an account to have already been selected and may be shared by multiple users. The input task ID or inferred conversation seed remains caller-scoped for routing. It never becomes a root ownership proof, a Codex fingerprint, a window grant, or a bypass of routing/access/capacity checks. Existing explicit sessions and opaque continuations retain their original rules. Native Codex, raw API relay, `off`/`device` convergence and disabled session affinity do not acquire this preference.

`diagnostics.bps_task_affinity` records `task_key`, `preferred_account_id`, `selected_account_id`, `result` and `persisted`. Results distinguish first binding, reuse, switching, concurrent selection, missing capacity and storage errors. Outbound `task_id` and `turn_id` remain available in the BPS identity diagnostics for comparison.
