# 关闭请求明细时保留轻量计量

系统设置 → 运行时 → 运行时优化：

- **使用日志写入**：选择 `off`，不写请求明细；需要错误排查时可选择 `errors`。
- **轻量计量（保留计费与 Token）**：保持开启，配置字段为 `usage_metering_enabled`，默认 `true`。
- 批量大小和刷新间隔沿用原有设置，默认 200 条 / 5 秒。可先保留默认值，再根据写入延迟、队列长度和实际流量调整。

管理员设置接口 `PUT /api/admin/settings` 支持部分更新：

```json
{
  "usage_log_mode": "off",
  "usage_metering_enabled": true
}
```

该开关保存到 `system_settings`，成功保存后在当前实例生效，重启后读取。多个进程共享数据库时，其他实例沿用现有运行时设置机制，需要分别应用或重启以加载配置。它不是 `CODEX2API_POLICY_*` 环境变量，也不控制 NewAPI 自身的日志。

## 各种组合

| 明细模式 | 轻量计量 | 实际写入 |
| --- | --- | --- |
| `full` | 开或关 | 每个事件写一次完整日志，不额外复制计量记录 |
| `errors` | 开 | 错误写完整日志，其余事件写精简计量 |
| `off` | 开 | 只写精简计量，不写 `usage_logs` |
| `errors` / `off` | 关 | 保留旧行为：仍扣累计金额，但被省略事件的 Token 统计和窗口额度会漏算 |

需要正常计费和窗口限制时，不要同时关闭明细与轻量计量。已经在旧版关闭日志期间缺失的事件无法自动补回。

## 保留什么、节省什么

新增 `usage_metering` 表，仅保留金额、各种 Token 数、时间、账号及凭据代次、API Key ID/显示标签、渠道、模型、端点、状态码和少量统计分类。Token 包括输入、输出、推理、缓存读取/写入及图片 Token，金额直接使用原有定价计算结果，不重新估算。

- 不保存诊断 JSON、IP、UA、请求/响应正文、完整错误信息和跟踪 ID；仅用一个布尔分类保留 overload 健康统计。
- 跳过无须保存的明细字段处理，避免异步队列持有大段诊断或错误内容。
- 每条 INSERT 从完整日志的 72 个参数减少到 39 个，采用批量写入，仅保留时间、Key＋时间、账号＋时间三个辅助索引。
- `usage_metered_events` 是统计用 `UNION ALL` 视图，合并完整日志与精简记录；不复制历史数据。请求列表、明细查看和导出仍只读完整日志。
- 精简记录、API Key 扣费、scope 累计计数与全局汇总在同一事务提交，失败一起回滚。不会因为切换模式而重复统计同一个事件。
- 保留逐事件时间，不用分钟/小时粗粒度桶替代滑动额度边界。Key、账号、模型、渠道、图表及用量自助页的统计均接入合并数据源。

API Key 金额、scope 计数、账号/会话状态以及独立的安全审计、服务错误和会话错误采集仍可能写入；本开关不表示整个应用零写入。

## 持久性和清理边界

轻量计量与原日志队列共用批量刷新机制，仍有刷新延迟。本次改动不引入逐请求同步落盘或持久队列：进程异常退出、长时间数据库故障造成的队列溢出，仍有原队列的数据丢失风险。额度统计也不是实时预扣，无法据此承诺高并发下零超额。

清理请求日志不会删除已写入的轻量计量，也不会把它再次加进累计基线。原有完整日志的清理/归档语义仍然保留：归档可保存累计及部分账号统计，但不会恢复已删除明细对应的精确 Key 窗口。精简记录暂不自动过期，以免破坏精确窗口或历史统计；高流量部署仍需关注数据库容量。

## 验证与性能结果

2026-09-28，本地 PostgreSQL 16.4，Windows、Ryzen 7 5800H、约 16 GiB 内存；`fsync`、`synchronous_commit`、`full_page_writes` 均开启。每组 12,000 条，200 条/事务，16 个 Key/账号，单写入 worker，完整日志带 2 KiB 合成诊断数据。交替运行三组并取中位数：

| 指标 | 完整日志 | 关闭明细＋轻量计量 |
| --- | ---: | ---: |
| 写入吞吐 | 9,463 条/秒 | 25,615 条/秒 |
| 12,000 条写入耗时 | 1.268 秒 | 0.468 秒 |
| WAL 增量 | 约 44.44 MiB | 约 6.89 MiB |
| 两张事件表及索引增量 | 约 41.69 MiB | 约 3.74 MiB |

吞吐约为 2.71 倍，WAL 减少约 84.5%，表及索引增量减少约 91.0%。这是数据库提交路径的受控测量，不包含上游响应时间、请求诊断采集、HTTP 并发及网络瓶颈，也不是 196 GB 生产服务器的 RPM 容量承诺。不同日志大小、硬件和并发条件会改变收益。

测试覆盖三种模式的金额和 12 个 Token 维度一致性、5h/1d/7d/30d 窗口、各统计入口、取消/内部请求、模式切换、清理后重建、重启、旧库升级、事务回滚、精确时间边界及大批次拆分。PostgreSQL 验证了统计视图的索引使用。

常规测试：`go test ./database ./admin ./proxy .`，前端 `npm run typecheck`、`npm run build`。

PostgreSQL 功能测试设置 `CODEX2API_METERING_TEST_POSTGRES_DSN` 后运行 `go test ./database -run '^TestUsageMetering' -count=1`。请使用本地可丢弃实例；测试创建并删除独立 schema。额外设置 `CODEX2API_METERING_PERF=1` 可运行 `TestUsageMeteringPostgresPerformance`，输出每组原始性能 JSON。
