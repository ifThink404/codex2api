# 服务错误日志

管理端运行页面顶部新增「服务错误」，地址 `/admin/ops/service-errors`。此处记录 **Codex2API 产生的代理请求拒绝或服务异常**，与既有账号/上游错误日志分开存储。

## 采集边界

- 覆盖 `/v1`、`/v1beta`、Codex 直连端点及对应无前缀代理路由。全局 RPM 限流、请求体校验在 API Key 鉴权前拒绝时也会记录。
- 标准本地 API 错误覆盖 Key 鉴权、额度/并发限制、主根等待、窗口/扩容准入、策略校验和调度失败。无上游调用的旧式 HTTP 错误由入口兜底采集；已经开始 SSE 的本地调度失败也记录。
- Responses / Realtime 的本地 WS 错误帧按逻辑请求采集，不等连接关闭；同一请求只记一次，同一连接后续请求重新计数。`status_code` 是该错误对应的状态，不代表 WS 的 101 握手状态。
- 上游账号的 401、429、额度耗尽、上游过载等仍留在原「错误日志」，不按状态码或是否具有账号 ID 混入服务错误。
- 不采集 NewAPI 在转发前的拒绝、管理页面请求、成功请求正文或任意进程控制台日志。此功能不是所有网络设备/上游错误的统一日志收集器。
- 仅升级后生效，历史未记录的错误无法补录。不改变客户端错误状态、错误正文、现有重试策略或账号健康判断。

## 可查信息

记录时间、错误状态/代码/消息、发生阶段、端点、HTTP/SSE/WS、模型、耗时、API Key ID/名称、请求 ID，以及已获取的请求分类、线程/窗口、根指纹、scope 和候选拒绝原因。尚未解析或鉴权的字段为空或 `unknown`，不会为补日志重新读取请求正文、校验签名或查询账号。

HTTP 响应中的 `X-Codex2API-Request-ID` 可用于定位。`newapi_request_id` 在前置拦截时可来自未经验证的请求头，仅用于搜索；以 `newapi_identity_verified` 区分签名元数据已验证的请求，不能把日志里的 ID 当成授权依据。原始客户端头部中的线程来源同样不是被动请求授权结论。

不保存 Authorization、密钥、原始请求正文或完整请求头；消息脱敏后最多 2 KiB，标识与数组长度均受限。不会写入用量表、产生费用或增加账号错误计数。

`client_info` 补充按来源标注的安装/设备 ID、UA、Originator、版本与实际携带的 SDK/系统信息。UUID 保留，非 UUID 设备身份哈希化；不合并有差异的来源，也不会用旧 WS 帧补齐设备身份。最多 24 个字段、键值合计约 4 KiB；原始设备和上游账号收敛后的设备不是同一概念。

## 性能与保留

- 单进程有界队列 512 条，单写入协程，最多每批 64 条；不足一批每秒写入。请求热路径不等待数据库，不为每个错误启动协程。
- 正常 HTTP/SSE 正文不复制、不缓冲；兼容旧式错误响应仅暂存最多 8 KiB。WS 显式记录错误，不拦截/扫描整个消息流。
- SQLite 和 PostgreSQL 共用独立 `service_error_events` 表，时间、状态、阶段和两种请求 ID 建索引。使用游标分页，每页最多 100 条；请求 ID 精确匹配，不对完整 JSON 执行模糊扫描。
- 默认保留 7 天及约最近 100,000 条，每分钟后台清理。写入/清理各限时 2 秒；管理员查询限时 3 秒，最多查 7 天。
- 页面首页可见时每 30 秒刷新，历史分页和隐藏页面不轮询。页面切换查询会取消旧请求。
- 队列满、写入失败不会阻断正常转发，也不会无界积压；页面展示本次进程启动后的待写入、队列丢弃、写入失败计数，控制台限频告警。异常关闭仍可能丢失队列中尚未落库的记录。
- 正常退出会尝试排空队列，超过 3 秒取消后退出；已落库记录跨重启保留，多实例共用数据库时每个实例的采集器计数独立。

## 管理接口

`GET /api/admin/ops/service-errors`，使用既有管理员鉴权。

参数：成对 RFC3339 `start/end`（默认最近一小时）、`status`（`429`/`4xx`/`5xx`）、`stage`、`request_id`（匹配 Codex2API 或 NewAPI 请求 ID）、`cursor`、`limit`（默认 20，上限 100）。返回 `items`、`next_cursor`、当前筛选的 `summary` 和本实例的 `collector`。

### 重复错误收敛

页面默认「收敛显示」，可切换「逐条显示」。API 使用 `grouped=true` 开启分组，省略时保持原有逐条返回。分组依据调用方（优先已验证 NewAPI 用户，否则使用已有作用域／会话标识）、API Key、接口、传输方式、模型、状态码、错误码、阶段及错误原因；不同已知调用方和候选拒绝原因不会混在一起。请求 ID、时间、窗口号、耗时和用户名变化不拆组，错误说明中当前请求 ID 会归一化，其他说明保持精确比较。

分组先应用时间、状态、阶段和请求 ID 筛选，再统计并分页，次数不局限于当前 20 条。每组用最近一条原始请求代表，`group` 包含 `key`、`count`、`first_seen`、`last_seen`；按最近发生时间及代表记录 ID 倒序。顶部总数和状态统计仍是原始错误次数，`summary.groups` 是当前筛选下的组数。分组与逐条视图的游标不能混用。

点击次数后，以 `grouped=false&group_key=<key>` 查看该组原始请求；保留打开分组时的筛选时间范围，可逐条分页查看并复制诊断，也可继续精确查询 NewAPI 请求 ID。原始记录不会被删除或合并写入。

新增索引化 `group_key` 列；现有日志在启动后的后台任务中按 128 条一批补齐，不阻塞启动或扫描整份 JSON 来完成每次列表查询。尚未补齐的记录暂时逐条显示，`summary.grouping_pending` 显示当前筛选范围内的待整理数量。原有 7 天／10 万条保留策略不变，分组次数随筛选范围及清理结果计算。

换号候选的 `outbound_identity_unavailable` 诊断增加 `account_failover.selection.candidates[].identity_failure`：包含 `stage`、`status`、`code` 和可选 `http_status`，区分根身份、身份存储、映射策略、窗口／轮次映射、别名登记与归属登记失败。只记录内部阶段枚举和状态，不保存底层错误正文、数据库凭据或原始会话 ID。
